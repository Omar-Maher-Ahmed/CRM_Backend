# 🧠 المعمارية، المبادئ البرمجية، والخوارزميات 

تم تصميم تطبيق الـ CRM بالاعتماد على أفضل الممارسات البرمجية لضمان كود نظيف، قابل للاختبار، وقابل للتوسع.

## 🏗️ 1. البرمجة كائنية التوجه (OOP)
بنية NestJS مبنية بالأساس على مفاهيم الـ OOP، وقد استخدمنا المفاهيم التالية بوضوح:

- **التغليف (Encapsulation):**
  - تم جعل وظائف الـ Repository بداخل الـ Services `private`. لا يمكن لأي كلاس خارجي التعديل مباشرة على قاعدة البيانات، بل يجب المرور عبر الدوال المتوفرة في الـ Service.
- **الوراثة (Inheritance):**
  - استخدمنا `PartialType` في الـ DTOs. على سبيل المثال `UpdateUserInput` يرث جميع خصائص `CreateUserInput` ويجعلها اختيارية (Optional)، مما يمنع تكرار الكود.
- **التجريد (Abstraction):**
  - الـ Controllers (أو الـ Resolvers في GraphQL) مجردة تماماً من التفاصيل المعقدة لقواعد البيانات. وظيفتها فقط استلام الطلب وتمريره للـ Service المختص.

## 📐 2. مبادئ SOLID
تم تطبيق مبادئ SOLID بقوة بفضل طبيعة عمل إطار NestJS:

1. **Single Responsibility Principle (SRP) - مبدأ المسؤولية الواحدة:**
   - كل ملف له وظيفة واحدة فقط:
     - `Entity`: يحدد شكل قاعدة البيانات.
     - `DTO`: يحدد شكل البيانات القادمة من الـ Client ويتحقق منها.
     - `Service`: يعالج الـ Business Logic.
     - `Resolver`: يتعامل فقط مع توجيه الطلبات للـ GraphQL.
2. **Open/Closed Principle (OCP) - مبدأ المفتوح والمغلق:**
   - عندما قمنا بإنشاء أنظمة جديدة (مثل `Customer` أو `Roles`)، لم نحتاج لتعديل النظام الأصلي ليعمل. الكود مفتوح للإضافات (عن طريق إضافة Modules جديدة) ومغلق أمام التعديلات الكبيرة في النواة.
3. **Dependency Inversion Principle (DIP) - مبدأ انعكاس التبعية:**
   - لا تقوم الكلاسات بإنشاء النسخ بنفسها `new User()`. بدلاً من ذلك، نستخدم آلية الـ **Dependency Injection (DI)** في الـ Constructor (مثل `@InjectRepository`). مما يسهل استبدال قواعد البيانات أو كتابة اختبارات Mock بسهولة.

## ⚙️ 3. الخوارزميات وأنماط التصميم (Algorithms & Design Patterns)

- **نمط المستودع (Repository Pattern):**
  - استخدمنا TypeORM الذي يطبق نمط الـ Data Mapper و الـ Repository. جميع استعلامات الـ Database معزولة داخل Repositories، مما يعني أننا لم نكتب أي أكواد SQL صريحة ومباشرة (Raw SQL)، مما يحمي النظام من الـ SQL Injections ويسهل التغيير لمحرك Database آخر مستقبلاً.
- **نمط المزين (Decorator Pattern):**
  - مليء في الكود: `@Injectable()`, `@Resolver()`, `@Mutation()`. يسمح هذا النمط بإضافة خصائص ديناميكية للكلاسات والدوال بدون تعديل بنيتها الأصلية.
- **نمط نقل البيانات (DTO - Data Transfer Object):**
  - لتقييد وتحديد شكل البيانات المتناقلة بين العميل والخادم، لمنع استقبال حقول غير متوقعة.
- **التعمية والتشفير (Hashing Algorithm):**
  - تم استخدام خوارزمية **Bcrypt** لتشفير كلمات المرور. لا يتم حفظ الباسورد بصيغته العادية إطلاقاً، بل كـ Hash غير قابل للكسر لتأمين المستخدمين.
